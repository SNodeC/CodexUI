## R03: measured limitation and approval request

The existing browser implementation maps every loaded thread row and every correlated agent directly into React elements. There is no existing scroll-window implementation in these list renderers. The conversation's bounded projection does not provide a reusable variable-height list window for these surfaces.

With complete lineage metadata, the checkpoint browser build populated 10,000 threads in approximately **1.73 s**, retained approximately **70,335 DOM elements** across the document, and took approximately **31 ms** for subsequent scroll and focus actions. With 10,000 correlated agents, ingestion took approximately **113 ms**, switching to Agents approximately **1.14 s**, subsequent scrolling approximately **32 ms**, and the combined document retained approximately **211,076 DOM elements**. These are single local fixture measurements, not percentiles, live-provider timings or cross-machine guarantees.

An earlier incomplete-metadata fixture took approximately 21.5 s and triggered approximately 10,000 metadata reads. That result includes lineage discovery and is not presented as list-rendering cost. The complete-metadata run separates that dependency. A production repair must preserve the existing lineage/admission policy rather than introducing an unrelated hydration limit.

Deleting data or replacing scroll navigation with an arbitrary displayed-entry cap would violate the requested behavior. CSS-only containment would retain all React elements and DOM residency, so it would not restore bounded list ownership. The proposed correction is one shared scroll-window implementation for both consumers, retaining their existing row components and all logical entries. It must use the existing parent scroll surfaces, preserve project body scrolling and standalone section cards, key measured geometry by semantic identity, retain focus/selection, and integrate logical keyboard navigation so Home/End and arrows can reach offscreen entries. No second row renderer, protocol store or server-side destination limit is proposed.

The estimated addition is 90–130 net production lines. The checkpoint adds 102 net production lines, and the current repairs add 107, for 209 combined. Windowing would bring the combined change to approximately 299–339 net production lines; implementing it therefore also needs approval to raise the combined cap from 250 to 340. The repair phase itself would remain below 250 net production lines. No such increase has been assumed or spent. Required checks include 10,000 entries; DOM/resident-row bounds; complete hydration-to-interaction timing; first/last and offscreen keyboard navigation; selection and expansion during updates; normal/coarse pointers; widths and fonts; and preservation of independent project scrolling. These estimates must be checked against the implementation rather than met by compressing code.

Approval was requested because the global [engineering instructions](/home/voc/.codex/AGENTS.md) require explicit approval before architectural extensions independently of LOC. Completing R03 also needs the combined production cap raised to 340 as quantified above. Both remain unapproved; elapsed time is not treated as approval.
